## Known lab traps (read first)

1. Wait for the blue "resources being provisioned" message to finish (2–5 minutes). Commands fail until the cluster exists.
2. The lab's cordon and drain loops use dollar-sign variables, which get mangled when copied. Here they're single commands with a node-pool label instead.
3. Click "Managing a Regional Cluster" before you delete pod-2. There's a STOP line before that step.
4. The ping steps open an interactive shell inside pod-1. Here each ping runs as one command that finishes by itself, so you never get stuck inside the pod.
5. The checker lags. If a check shows 0 right after a successful step, wait 30–60 seconds and click again.
6. Flow logs ARE scored. The last checkpoint (Simulate Traffic) checks three things: flow logs on the subnet, a sink named FlowLogsSample, and the BigQuery zone query (src_instance / dest_instance) on cross-zone traffic. Skip them and you finish at 85/100.
7. Student accounts can't change project IAM, so the lab's IAM step for the sink fails. Here the sink gets write access on the dataset instead, which works.
8. Order matters. Flow logs and the sink must exist BEFORE the cross-zone ping, and the zone query (src_instance / dest_instance) must run BEFORE the pods move onto the same node. Same-node traffic never leaves the VM, so it never shows up in flow logs.

Block 2 – pod-1 and pod-2, on different nodes:

```bash
cd ~
cat > pod-1.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: pod-1
  labels:
    security: demo
spec:
  containers:
  - name: container-1
    image: wbitt/network-multitool

cat > pod-2.yaml <<'EOF'

  name: pod-2
```

## Task 4 – Flow logs, sink and cross-zone query (scored)

Block 1 – turn on flow logs for the subnet, with full metadata:

```bash
gcloud compute networks subnets update default --region=`cat ~/region` \
  --enable-flow-logs --logging-metadata=include-all --logging-aggregation-interval=interval-5-sec
gcloud compute networks subnets describe default --region=`cat ~/region` --format="value(enableFlowLogs)"
```

It should print True. Don't skip `--logging-metadata=include-all`. Without it, the logs have no zone or VM fields, Block 4 never finishes, and Block 5 fails with "src_instance does not exist". To confirm, run `gcloud compute networks subnets describe default --region=$(cat ~/region) --format="value(logConfig.metadata)"`. It should print INCLUDE_ALL_METADATA.

Block 2 – BigQuery dataset, the FlowLogsSample sink, and write access on the dataset:

```bash
export PROJECT_ID=`cat ~/project`
bq mk --dataset --location=US ${PROJECT_ID}:us_flow_logs
gcloud logging sinks create FlowLogsSample \
  bigquery.googleapis.com/projects/${PROJECT_ID}/datasets/us_flow_logs \
  --log-filter="resource.type=\"gce_subnetwork\" AND logName=\"projects/${PROJECT_ID}/logs/compute.googleapis.com%2Fvpc_flows\""
SA=$(gcloud logging sinks describe FlowLogsSample --format="value(writerIdentity)" | sed 's/serviceAccount://')
bq show --format=prettyjson ${PROJECT_ID}:us_flow_logs > ds.json
jq --arg sa "$SA" '.access += [{"role":"WRITER","userByEmail":$sa}]' ds.json > ds_new.json
bq update --source ds_new.json ${PROJECT_ID}:us_flow_logs
```

Block 3 – ping across zones (finishes by itself):

```bash
kubectl exec pod-1 -- ping -c 60 `kubectl get pod pod-2 -o jsonpath='{.status.podIP}'`
```

Note the average time on the last line (rtt min/avg/max).

Block 4 – wait for the zone fields to land in BigQuery (usually 5–10 minutes):

```bash
export PROJECT_ID=`cat ~/project`
export TABLE=compute_googleapis_com_vpc_flows_`date -u +%Y%m%d`
until bq show --schema --format=prettyjson ${PROJECT_ID}:us_flow_logs.${TABLE} 2>/dev/null | grep -q src_instance; do echo "waiting for src_instance..."; sleep 30; done
echo "Zone fields are in."
```

If it's still waiting after about 8 minutes, open a second Cloud Shell tab and run Block 3 again. Both pods must still be on different nodes. If you're not sure, run `kubectl get pod pod-1 pod-2 -o wide`.

Block 5 – the zone query (required: the checker looks for this exact query):

```bash
bq query --use_legacy_sql=false "
SELECT
  jsonPayload.src_instance.zone AS src_zone,
  jsonPayload.src_instance.vm_name AS src_vm,
  jsonPayload.dest_instance.zone AS dest_zone,
  jsonPayload.dest_instance.vm_name AS dest_vm
FROM \`${PROJECT_ID}.us_flow_logs.compute_googleapis_com_vpc_flows_*\`
WHERE jsonPayload.src_instance.zone IS NOT NULL"
```

You should see rows where src_zone and dest_zone are different zones. A plain traffic query (src_ip/dest_ip only) is NOT enough. It scores 15/20.

Check my progress: Simulate Traffic (20/20, for 100/100 total)

If it shows only part of the score, the red message tells you which piece is missing (flow logs, sink, or query). Re-run that block from Task 4 and click again.
